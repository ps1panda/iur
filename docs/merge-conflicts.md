# Почему возникают повторяющиеся merge-конфликты

Ниже — разбор типовой ситуации из ветки `work`, где из-за неаккуратного разрешения конфликта в `src/app/page.tsx` остались дублирующиеся блоки данных (`processSteps`, `ownerBenefits`, `partners`, `projects`). При следующей попытке объединить ветки Git снова «видит» изменения в этих же строках и запускает конфликт, даже если визуально страница работает.

> ⚙️ Теперь основная страница разбита на компоненты в `src/app/components/*` и собирается через `src/app/sections.ts`. Это уменьшает количество пересечений в одном файле. Если требуется изменить текст конкретного блока, правьте только одноимённый компонент (например, `Hero.tsx` или `Projects.tsx`).

## Корневые причины

1. **Несинхронизированная база ветки.** Чем дольше рабочая ветка живёт без `git pull --rebase origin main`, тем больше шанс, что нужные строки уже были переписаны в `main`.
2. **Разный порядок правок в больших массивах данных.** Если несколько людей одновременно редактируют один и тот же массив (например, добавляют пункты в `ownerBenefits`), Git не сможет автоматически решить, как их объединить.
3. **Неряшливое разрешение конфликта.** Когда вместо ручного объединения изменений конфликт просто «склеивается» (в репозитории остаются обе версии массива), Git фиксирует дальнейшие попытки их удалить как новые правки, провоцируя очередной конфликт.

## Как избежать

- Перед началом работы и перед коммитом выполняйте `git pull --rebase origin main`, чтобы ветка подтягивала актуальную версию `page.tsx`.
- Разбивайте большие массивы контента на отдельные модули. Мы вынесли данные шапки и секций в `src/app/data/content.ts`, чтобы разные разработчики реже пересекались в одном файле.
- При возникновении конфликта аккуратно объединяйте обе версии, удаляя все маркеры `<<<<<<<`, `=======`, `>>>>>>>` и проверяя, что в файле остался ровно один вариант каждого массива.
- После ручного мерджа обязательно запускайте `npm run lint` или `npm run build`, чтобы убедиться, что файл компилируется и не содержит дубликатов.

Следуя этим шагам, можно существенно сократить количество повторяющихся merge-конфликтов в ключевых файлах.
